# 2026-09-23 录音与照片导入失败分析

## 结论

截图对应的导入均在 `stage=connectingWifi` 失败：App 已观察到 IPv4 `192.168.0.2`，但未能建立到眼镜 `192.168.0.1:80` 的 TCP 连接，约 12 秒等待结束后抛出公共提示。尚未读取目录或下载文件，因此这些报错发生在文件处理之前。

录音失败包含明确的网络不可用错误；照片失败仅记录 TCP 超时，不能将两者的底层原因直接等同。日志不能进一步区分眼镜热点/端口服务未正常就绪、手机 Wi-Fi 路由不可用等原因。

## 已核实的边界

- 四轮导入的 `wificonfig` 原始 107 字节完全一致，声明 payload 95 字节；SSID 13 字节、口令 9 字节，均无首尾空白或 NUL。成功与失败使用相同配置，未发现配置截断或口令内容损坏证据。
- 录音、相册都获取本轮配置，再调用公共 `DeviceWifiManager.connect`，不从旧凭据缓存取值。
- 所有照片失败的 `closewifi` 都晚于热点等待超时，属于失败清理；不是提前关闭热点造成最初超时。录音首次失败时 BLE 未就绪，未能发送关闭命令。
- 失败轮次尚未进入 `fetchingList`，没有文件下载或删除步骤。后续成功录音的删除确认属于它自己的成功流程。
- `currentSSID=unavailable` 同时出现在失败和成功轮次；单凭此项不能证明未连接。现场通过 IPv4 网段兜底允许 TCP 探测，不能把“热点身份校验通过”当成已验证真实 SSID。
- 截图状态栏显示 5G 不足以定位失败原因，以接口、TCP 和 HTTP 记录为准。
- 同一文件服务错误文案可由热点检查或实际 HTTP 请求产生；本次由 `stage=connectingWifi` 和对应请求时序确定为前者。

## 版本与复现条件

日志标记 App 1.1.6 (126)、系统 Version 27.0 (Build 24A437)。BLE 回包显示：09:41 蓝牙/主固件为 `V01.01.01.21-beta1` / `V02.01.01.06-beta1`，09:52 后为 `.28-beta1` / `.08-beta1`；09:55 重连后仍为后者。现有日志未记录这次版本变化的成功升级过程，不能确定升级由何端完成，也不能把后续录音成功单独归因于重新配对。

09:55 的版本查询发送仍可见约 200ms 节奏；Wi-Fi 日志没有本任务新增的 `diagnosticID`、接口快照、`currentPath` 等字段。因此这组日志不能作为新增 3 秒间隔或网络诊断代码的验证结果。

下一次需用包含新增诊断的构建复现，关联 `diagnosticID` 查看 Wi-Fi 接口、默认/Wi-Fi 专用路径、每次 TCP 的状态与错误；若手机路径就绪而目标持续无响应，再结合眼镜端热点启动、关联及 TCP 80 监听日志定位。现有证据不足以承诺单纯延长 12 秒等待即可解决。

## 后续补充的 App 日志

针对本组故障，在此前接口、路径、SSID、凭据对照日志基础上补充：

- 录音/相册每轮导入在打开热点前生成 `diagnosticID`，配置获取、热点检查、TCP 探测、目录读取、终态与失败清理检查点共用该编号。显式标记 `import=recording/album`，避免依靠相邻时间猜测所属任务。
- 导入检查点和热点快照附带目标/当前外设、BLE ready/连接状态、App 缓存的运行状态及两个固件版本。明确 `deviceEvidenceSource=app_state_not_fresh_device_query`，不把缓存状态当成眼镜实时回执，不额外发送 BLE 查询。
- 失败日志保留错误 domain/code、发生阶段、任务取消标志与清理前状态；空录音目录也记录完整终态。
- TCP 增加连接路径和可用性变化记录；超时时保留最后连接状态、停留时长及历史 waiting 错误，区分一直建立连接与因网络不可用等待。历史错误不冒充当前错误；结束后清除观察回调，防止晚到日志串入下一轮。

初次补日志时，热点诊断标记 `diagnosticVersion=2`，导入检查点标记 `importDiagnosticVersion=1`，TCP 标记 `tcpDiagnosticVersion=2`；该批改动仅记录现场。后续按用户要求对齐 Android：热点改为最长 30 秒等待身份/IP，不再以独立 TCP 探测拦截；真正 HTTP 请求记录 `httpDiagnosticVersion=3`。当前行为见 [Android 对齐说明](2026-09-23-Android-Wifi-OTA-Alignment.md)。

眼镜端仍需记录热点启动结果、客户端关联/断开、IP 分配，以及 TCP 80 端口监听、接受连接与关闭原因。App 无法替代这些眼镜内部证据；手机路径显示可用也不能独自证明眼镜服务异常。
