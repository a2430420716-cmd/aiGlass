# 新手引导媒体事件与诊断

更新：2026-09-29。依据 Android `NewbieGuideActivity`、`BleManager` 和 `BleForegroundService`，补齐 iOS 引导播放器的媒体事件消费及导出日志。

## 协议与行为

| 页面步骤 | 下发 | 完成回包 | 对应媒体事件 |
| --- | --- | --- | --- |
| 4，播放 | `0x81 [04,00]` | `0x81 [04,01]` | `0x6A` |
| 6，下一首 | `0x81 [06,00]` | `0x81 [06,01]` | `0x6C` |
| 7，上一首 | `0x81 [07,00]` | `0x81 [07,01]` | `0x6D` |
| 8，暂停 | `0x81 [08,00]` | `0x81 [08,01]` | `0x6B` |

- 进入/切换仍下发 `[step,0]`，退出 `[0,0]`；只有当前步骤 `result=1` 才自动推进。媒体事件、状态通知和等待超时均不能充当完成回包。
- 媒体事件只操作本 App 的引导音乐，且须匹配当前步骤。Android 的系统级跨 App 媒体键分发没有被宣称为 iOS 已实现。
- `Gen1GuideStepState` 保证同一步动作至多执行一次：媒体先到则完成回包不重复切歌；完成回包先到则晚到媒体与新步骤不匹配，被忽略。
- 设备 UUID、绑定、页面会话 ID、回调采集时间均校验。旧页面按钮、已退出页面的回包、早于重新开始的排队回调不能推进新会话。
- 同设备重连只恢复未完成的当前步骤，保留已执行媒体动作标记。完成后即使页面仍显示完成页，也不因重连重新开启引导。切设备不会把旧步骤同步给新设备。
- 引导资源加载任务退出时取消，并校验页面会话；旧响应不能重新写入引导进度。

无线协议没有会话 ID，因此“新一轮开始后固件才生成的旧步骤回包”无法仅靠本地时间绝对区分；日志保留时间与步骤证据，不用定时器猜测完成。

## 导出日志

以下记录均进入 D 浮窗的蓝牙日志，无需连接 Xcode 控制台：

1. 页面开始、重新开始、手动跳过、步骤推进、完成、退出，关联 `session`、目标 UUID、当前步骤、等待步骤。
2. `Gen1 guide step requested / rejected / send result`：请求步骤、拒绝原因、是否入发送队列；`queued=true` 不代表设备确认。实际发送字节仍由已有 BLE 发送日志记录。
3. `Gen1 guide GATT callback`：通知来源、特征 UUID、是否当前连接/特征、采集时间、字节数、底层错误。在旧连接过滤之前记录。
4. `Gen1 guide control decode`：输入/缓存长度、完整帧数、仍等待包头或续包、CRC 失败、超长声明与噪声丢弃。
5. `Gen1 guide control frame received`：`0x81`、`0x6A–0x6D` 的原始小帧、步骤/结果、来源与处理器是否存在；异常长帧最多显示 96 字节并标明截断。
6. 控制器处理结果：接受、步骤不符、未完成、重复动作、设备不可用、页面/会话/目标失效，以及未注册处理器、短负载、设备忙、错误收发方。
7. 音乐播放/暂停/停止请求与结果：曲目、播放器是否存在、播放前后状态、资源缺失、音频会话/播放器错误、音频路由和系统中断。
8. 每 15 秒记录仍在等待的步骤、耗时和音乐/连接状态；只诊断，不自动跳过。连接日志保留断线原因，蓝牙日志另记重连恢复判断。

控制通知回调与重组诊断只记元数据。完整原始帧仅限上述引导/媒体命令，不扩展记录音频或 Wi-Fi 凭据。

## 真机复测

本地验证通过：控制解码诊断 2,225 条、引导事件状态 808 条、真实控制器集成 152 条断言；现有一代完整回归及共享蓝牙/二代回归通过，最终 iOS Debug 无签名编译成功。控制器测试提取实际生产类，仅替换 BLE、播放器、网络和进度存储；验证两种回包次序与会话生命周期，不实际播放音频或修改用户设置。

验证 4–8 步的音乐播放、切歌与暂停；第 8 步单击后应暂停并在 `0x81 [08,01]` 到达后进入第 9 步。若再次停住，导出蓝牙及连接日志，可分别判断无 GATT 回调、等待续包、CRC 拒绝、未完成回包、步骤错位或播放器失败。另测重复触控、手动跳过、等待中重连、完成页重连、退出后重进与切换设备。

本地模拟和无签名编译不替代眼镜真机验收；本轮不把前次缺少完成回包日志的现场认定为已确定固件故障。
